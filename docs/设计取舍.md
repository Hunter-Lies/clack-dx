# 设计取舍

这个工具做过的决定，以及为什么。踩过的坑记在这儿，省得下次再踩一遍。

## 为什么单独一个软件，不并进咔哒

DirectX 那 184 个 dll 解出来 222 MB，压进 zip 也有 80 多 MB。并进运行库合集，
那个 exe 会从 63 MB 涨到 150 MB 以上——对"只想补 VC++ 运行库"的人是白下 90 MB。

两个工具各管一摊，谁需要什么下什么。

## 只补缺的，不覆盖已有的

`SysWOW64` / `System32` 里的同名 dll 一律不动，只在文件不存在时才复制。三个理由：

1. 这些文件是**按名字共存**的（`d3dx9_43.dll` 就是 43 这一版），存在即正确，不存在"内容不对"这回事
2. 覆盖正在被程序加载的系统 dll 会直接失败（共享冲突），修一遍反而报一堆红
3. 覆盖是那类"顺带装运行库"的工具出问题的根源——它把新版顶掉了

## 为什么不打包 D3DCompiler_47.dll

DirectX 修复工具里带了这个（2017 年的版本），但官方 DX 分发包里没有——它是 Win10 1709 以后的系统组件。
我们的目标系统是 Win10 / 11，系统目录里本来就有，塞一个 2017 年的旧版本进去只会倒退。

## 为什么剔掉 Managed DirectX 程序集

官方分发包里有一包 `microsoft.directx.*.dll`（`Apr2006_MDX1_x86_Archive.cab`），
那是 Managed DirectX 的托管程序集，不是系统 dll：扔进 `System32` 既没用也不合适。
解包时按名字前缀直接排除，参考的那份工具也不收它们。

## 分组靠文件名前缀，不硬编码 184 个名字

`lib.rs` 里只有一张六个分组的前缀表（`d3dx9_`、`d3dx10`、……），
"这一组有哪些文件"是运行时扫 payload 目录得到的。
微软的命名很稳定（`d3dx9_24` ~ `d3dx9_43` 这么多年没变过），
硬编码 184 个文件名只会让以后换源包时到处改。

## 先数缺的，再要管理员权限

启动时先 `scan()` 一遍，六个分组里一个都不缺的话，按下去直接进"完成"，
不会为了什么都不做弹一次 UAC。

## payload 解到 ProgramData

`%ProgramData%\ClackDX\payload\<版本>\`，同一版本只解一次。
放临时目录的话每次启动都要解 222 MB；带上版本号是为了升级时自动换一份。

## 关窗口的兜底

复制过程中后端用 `BUSY` 拦掉 `CloseRequested`（Alt+F4、任务栏关闭、自己的关闭键都会走到那里）。
正常关窗口在极端情况下可能没生效，所以关闭键按下 500 ms 后再无条件 `std::process::exit(0)`。

## 跳转链接走 ShellExecuteW

界面上的作者 / 仓库两个键走 Rust 侧的 `open_url`（`ShellExecuteW`），
不用 WebView 的 `window.open`——那个在 WebView2 里要额外配权限，配不齐就变成在窗口里再开一个 WebView。

## 别给机身挂状态类名（踩过两次）

机身上原来挂着 `:class="phase"`，于是待机时它的 class 是 `console idle`、
修复中是 `console busy`……看着无害，但它把 CSS 变成了一片雷区：

- 给待机屏写的 `.idle { padding: 28px 16px 4px }` 直接命中了**机身本身**，
  机身的内边距被改成 28/4，整个页面往下错 12px——现象是"待机页底部没有间距"
- 卡片里的署名行复用了屏幕清单行的 `.row`，于是鼠标移上去那行会高亮

两条规矩：机身不挂状态类（没人用它）；内容块的类名要么带前缀（`.idle-pane`、
`.screen-status`），要么干脆别用通用词（`.line` 而不是 `.row`）。

## 调布局看 ?debug=1

dev 里在地址后面加 `?debug=1`，屏幕左上角会打出一行各块的实测上下沿：

```
DEBUG console=6..458 page=22..442 screen=22..442 deck=22..442 status=401..441 …
```

配合 headless 截图量像素，比肉眼猜"哪块矮了 10px"快得多。
这段代码在 `import.meta.env.DEV` 里，正式包会被摇掉。

## payload 只活到程序退出

184 个 dll 解出来 222 MB，比咔哒那边的 60 MB 大得多，"留着下次省一次解包"这笔账不划算——
这工具是隔很久才用一次的，没人愿意为省一两秒在 C 盘留 222 MB。

所以退出即清：`quit()` 命令里清一次（点关闭键那条路），`RunEvent::Exit` 里再清一次
（点窗口 X 那条路）。两处都清是故意的，这个操作幂等，删不存在的目录不报错。

两个例外：

- **用管理员权限重新拉起自己时不清**（`RELAUNCHING` 标志）。那条路上旧进程马上退场，
  新进程还要用 payload；新进程会自己负责退出时清理。
- 被任务管理器强杀或崩溃时来不及清，会留下目录——README 里写了手动删。

## 判定"对不对"：比固定版本，不比字符串

`FileVersion` 字符串不可靠：184 个文件里有 18 个长这样 `9.15.779.0000 (WGGT_OCT06.Release)`，
带后缀，按字符串比会把这 18 个健康文件全判成"异常"。

所以比的是 **VS_FIXEDFILEINFO**（版本资源里的四段数字），两边都用同一套读法：
`GetFileVersionInfoW` + `VerQueryValueW("\\")`，四段零补齐后逐段比。
payload 里 184 个文件的固定版本都不是 0，这条判定对全部文件有效。

**只往新了走**：目标版本 ≥ payload 就算好，哪怕字节不一样也不碰。
微软给部分 DX dll 发过安全更新，按"哈希不一致就覆盖"会把人家更新过的换成我们 payload 里的老版本
——那正是我们在别的工具身上批评过的事。

**覆盖不备份**：被覆盖的目标要么是坏的、要么是旧版，payload 里就是正确的；
往 System32 里堆 `.bak` 只会让下一个排查的人更迷惑。

## --verify-hash 是暗门

版本 + 大小能抓住绝大多数真实损坏（截断、被杀毒隔离成 0 字节、被老整合包降级、被顶替）。
剩下的"版本对、大小对、内容坏"（位翻转、坏道）只有全量比对能发现，代价是每次检测多读约 500 MB。
所以它不进主流程，做成命令行开关，由懂的人自己加。

比对是**逐字节**做的，不是算哈希：少一个依赖，而且逐字节比哈希更强（任何差异都逃不掉）。
